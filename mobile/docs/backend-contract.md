# Mobile/backend integration checklist

These are the mobile frontend's requirements, derived from the manuscript and latest ERD. The first beneficiary-account endpoints now live in `../../backend`; the remaining rows describe later milestones.

The original local API below remains available. The [shared staff-backend integration](shared-backend-integration.md) implements registration/OTP/sessions/profiles, document intake/review/corrections, `GET /beneficiaries/me/overview`, `POST /beneficiaries/me/claim-pass`, `GET /beneficiaries/me/wallet`, `GET /beneficiaries/me/notifications` and `PATCH /beneficiaries/me/notifications/:notificationId/read` under `/api/v1/mobile` in the teammate's backend checkout. Keep its schema, sessions, migrations, and data separate from the original local backend.

The shared extension is reconciled with staff backend version 4.0 (`42b4552`) via the consolidated `mobile-v4.patch`. It respects staff document removal, preserves named Other requirements during corrections, and reuses upstream QR_OR_BIOMETRIC rules. Creating physical-assistance events now requires package details. No mobile production API shape changed for this update.

Shared documents use multipart `documentType` and `file`, unlike the original raw-byte protocol below. Their public DTO adds `reviewNotes`, `reviewedAt`, `replacesDocumentId`, and `canReplace`. Staff SUBMITTED/ACCEPTED/REJECTED/SUPERSEDED map to mobile received/accepted/rejected/superseded. `POST /beneficiaries/me/documents/:documentId/replacement` corrects an owned rejected document with the same category. There is no beneficiary review endpoint. Document acceptance does not approve enrollment or identity.

The shared overview preserves the mobile contract, adding optional `reviewNotes` and `reviewedAt` to enrollments and allowing null program grant amounts. It returns only the signed-in account's enrollments and earliest eligible published schedule. The assigned slot supplies its Manila date/time and venue. Draft/closed/cancelled events, inactive programs, unapproved/cancelled/claimed allocations, closed slots, missed/cancelled schedules, and expired slots do not produce an upcoming schedule. FULL slots remain visible to their assigned beneficiary. The API is read-only and does not approve eligibility or create assignments.

The shared claim-pass endpoint returns the same DTO as the original route below. Only an eligible own-account assignment in a QR-enabled distribution can issue a pass. Reopening preserves a mobile-issued credential; revoked/expired/used tokens and other processed claims are blocked. A staff biometric-first pending combined-verification claim can still show its outstanding QR. Separately staff-issued credentials return `CLAIM_PASS_STAFF_ISSUED` rather than being overwritten. Conflicts return `QR_CLAIM_CONCURRENT_CHANGE`. Staff verification consumes the shared token; this mobile endpoint never completes a claim, bypasses biometrics, releases assistance or credits a wallet.

## Shared biometric consent and status (phase 8)

All three routes require a beneficiary mobile session: GET `/beneficiaries/me/biometrics`, POST `/beneficiaries/me/biometric-consents`, POST `/beneficiaries/me/biometric-consents/:consentId/revoke`. Owner identity comes from the session. Giving consent sends `{ consentVersion, retentionUntil, expectedConsentId }`, using the reviewed GET policy. Responses use `{ data: { enrollmentMethod, processorMode, policy, consent, profile } }`. Consent includes ID/version/status/timestamps/retention; profile includes ID/consentId/status/simulated/processorCompatible/enrolledAt/lastVerifiedAt. No captures/templates/scores/other identities are returned. Status may be enrolled, pending_duplicate_review, duplicate_blocked, revoked, expired or consent_required. Stale consent changes return 409; foreign withdrawals return 404. See [biometrics setup](biometrics-setup.md).

Only staff capture and enroll faces. Mobile consent alone never creates a profile; renewing consent never restores a revoked one. SIMULATED records remain clearly labeled. This replaces the earlier client-only consent/camera preview; the original mobile API below has no biometric endpoints.

## Shared staff-support requests (phase 9)

GET `/beneficiaries/me/support?page=1&pageSize=20` returns `{ data: { requests, pagination } }`. POST on the same path takes `{ requestId, language: 'en' | 'bs', messageText }`. GET `/beneficiaries/me/support/:requestId` returns `{ data: { request, messages } }`; POST `/:requestId/messages` takes `{ messageId, messageText }` and returns the saved thread. IDs are UUID retry identifiers, not credentials. Request metadata includes status, dates, resolution, retention and canReply. Messages include only id, role, text and createdAt. The signed-in mobile session supplies ownership, and the source marker excludes anonymous chatbot conversations. Staff replies/resolution use the existing scoped staff endpoints. Replays return the saved thread; altered IDs/content, closed requests and concurrent changes may return 409. Foreign/expired-retention requests return 404. No external AI, push, attachments or automatic translation is added; refresh loads updates. See [support setup](support-setup.md).

## Shared document checklists and names (phase 10)

GET `/beneficiaries/me/document-requirements?page=1&pageSize=10` returns `{ data: { programs, pagination } }`; pageSize is capped at 20. Programs contain only id/code/name/status and requirements `{ docType, documentName }`. ACTIVE programs are visible for preparation; CLOSED programs require an enrollment owned by the signed-in beneficiary. Draft/cancelled and foreign closed-program records are excluded. No criteria, budget or staff fields are exposed; a checklist does not confirm eligibility. Shared document DTOs add nullable documentName. Multipart uploads can send it for OTHER; a correction preserves its original name and rejects a different one with DOCUMENT_NAME_MISMATCH. The original API below has no checklist/name feature. See [document checklists](document-checklists.md).

## Implemented original mobile API

Phase 7 keeps the existing registration/code-request/verification endpoints. Optional SMS mode uses a private Semaphore key and never returns a development code or raw gateway response. Challenge creation commits before sending, delivery must be accepted before verification, and failed sends invalidate that challenge. OTP/session mode binding rejects development credentials in SMS mode. Registration and code-request clients allow 20 seconds for delivery/database work. Recover account uses the existing login purpose; it does not reset a password, change a number or link a staff record. The adapter is prepared but unactivated because the team has no provider account. See [SMS setup](sms-setup.md).

Shared in-app notifications preserve the existing DTO and use a new additive migration for optional Bisaya text and first-read timestamps. The owner comes from the mobile session. Only IN_APP messages with SENT/READ status and a nonfuture sent time are visible; linked schedules must have the same owner. Concurrent/retried reads keep the first timestamp and leave staff delivery status untouched. Staff transitions insert controlled notices transactionally and skip duplicate event keys. Draft scheduling/cancellation does not notify; existing staff rules lock changes after publication. This inbox does not send SMS/push or depend on Redis. Apply `mobile-notifications.patch` after the preceding two version-4 patches.

The shared wallet endpoint preserves `wallet`, `currentClaim`, `claims` and `transactions`. Claim metadata adds optional `deliveryMode`, `verifiedAt`, `releasedAt`, `package` (name/unit/quantity), `receipt` (number/issuedAt) and `needsReview`. The current claim comes from the eligible upcoming assignment; saved history includes closed events. Values come from allocations, dates from assigned Manila sessions. Physical CLAIMED records display Released, while VERIFIED displays awaiting release. Missing accounts return null without creating a wallet. Only own claim-linked BENEFIT_CREDIT and BENEFIT_REVERSAL entries are returned, with signed amounts; transfers are excluded. Receipt snapshots, staff fields, release notes, QR secrets and dispute text are not exposed. Apply the incremental `mobile-claims.patch` after `mobile-v4.patch`.

The mobile app centralizes API calls with a timeout, loading/error states, server-issued codes, persistent sessions, and protected signed-in routes. Claim and wallet data are display-only in the beneficiary app. The future staff endpoint must verify the claim and create the associated transaction in one database transaction so partial completion cannot occur. Do not embed database, SMS, or biometric-service credentials in Expo public environment variables.

Notification responses use `{ data: [...] }`, with each entry containing `id`, `scheduleId`, `title`, `titleBs`, `message`, `messageBs`, `notificationType`, `sentAt`, and `readAt`. PATCH returns `{ data: { id, readAt } }`. Delivery `status` remains separate from `readAt`; inbox queries include only `channel: in_app`, `status: sent`, and `sentAt <= now`. Other beneficiaries' IDs return 404 on PATCH. Dates are ISO timestamps, displayed in Manila time. The mobile inbox refreshes when opened and on demand; there is no polling or OS push delivery.

Profile PATCH accepts a partial JSON object containing only `firstName`, `middleName`, `lastName`, `address`, and `barangayId`, and returns `{ data: Beneficiary }` in the same shape as GET. Names are trimmed, limited to 100 characters, and accept Unicode letters with normal name punctuation. Blank/null `middleName` clears it. Addresses require 5–500 characters. A new barangay must be active; keeping the existing one is allowed even if it has become inactive. Empty bodies, unsupported fields, and invalid input return 422; field errors use `error.fields`. Ownership always comes from the bearer session, never a supplied beneficiary ID. The mobile form sends only these five editable fields and updates its shared profile cache after server confirmation.

The team's staff backend should create a notification in the same database transaction as a schedule change or completed claim. Set the recipient from the authorized event, verify ownership of any linked schedule, supply the message and optional translation, and leave `readAt` null. The beneficiary app cannot create notifications or complete claims. The seed includes two historical demo messages and preserves their read timestamps when rerun.

Add offline schedule/pass caching only after agreeing token expiry and revocation behavior. The current pass is held only while its screen is open and is reissued by the server when opened again.

Document POST sends raw bytes, not multipart or JSON. It requires the bearer token, a matching `Content-Type`, percent-encoded original filename in `X-File-Name`, and `X-Document-Type` set to `proof_of_residency`, `valid_id`, or `other`. New uploads return 201; identical bytes/category/account return the existing record with 200, including concurrent retries. List/upload envelopes use `data`; records contain `id`, `docType`, `originalName`, `mimeType`, `sizeBytes`, `status`, and ISO `createdAt`. Empty/invalid metadata returns 422, oversize 413, and unsupported/mismatched file types 415. File downloads return 404 for an unknown ID or another beneficiary's file. File paths and content hashes are not returned.

The default store is Git-ignored `backend/storage/documents/`; `DOCUMENT_STORAGE_DIR` can configure a private location. Byte writes and failed database inserts are cleaned up during normal errors. A shared deployment needs durable private storage and coordinated backup/retention cleanup. The current ERD-aligned beneficiary document relation represents self-uploads; no staff `uploaded_by` FK is added before the shared staff-user model exists. The mobile screen lists saved records and received state; staff approval and file-viewing UI remain separate.
